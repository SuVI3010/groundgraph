Meet GroundGraph, a graph-native recovery command center for airport operations. This is a bounded replay of Chicago O'Hare demand from eight A.M. to noon on January twelfth, twenty twenty-four. It is an ATC-inspired research sandbox, not a live control system.

The replay separates evidence clearly. Selected flight schedule, runway, and time-gated weather fields come from public B.T.S., F.A.A., and NOAA records. Gates, ground events, operational effects, policies, and every recovery outcome are modeled. Each replay entity links to a stable source record through `SOURCED_FROM` or `MODELED_BY`, with its observed and modeled fields listed separately.

At the disruption checkpoint, a modeled baggage-reconciliation delay adds twelve minutes to the stored turnaround task graph for the UA fourteen fourteen to UA twenty-six seventy-two rotation.

Six specialists now execute real domain Cypher reads against the same FalkorDB version: weather, runway flow, compatible gates, turnaround dependencies, current policy, and contextual memory. The Cycles view shows all six query names, evidence identifiers, overlapping start and end timestamps, input version, and consumed handoffs. The coordinator cannot choose a plan until those graph records exist.

GroundGraph builds three materially different strategies: flow balance, compatible gate swap, and turnaround-task recovery. Projected recovery and operational burden come from the connected graph state. Cost score is a cost, so lower is better. The server computes the full safe non-dominated ranking, then creates a context-bounded model shortlist. For a turnaround event class, candidates must be within four cost points of the ranking leader; other event classes use eight. Only those shortlist identifiers enter the Model Run allowlist, and local Qwen may choose one of them. An invalid response activates the labeled deterministic fallback.

The visible causal path is also graph proof, not a generated story. It is queried after the selected actions are stored. The affected flight reaches an action through `RECOVERED_BY`; the action reaches its runway or gate through `USES_RESOURCE`, its turnaround through `REORDERS`, or its next flight through `PROTECTS`. `AUTHORIZED_BY` and `SUPPORTED_BY` continue into the current procedure evidence. Every displayed hop already exists in FalkorDB.

Before application, the server rechecks graph version, current policy, source freshness, required relationships, the execution freeze, minimum benefit, and the churn guard. The autonomy switch changes the server setting. With guarded autonomy enabled, current synthetic policy authorizes application; with it disabled, the same proposal waits for manual approval.

Application writes the complete Decision Episode to Plan to Outcome and Memory lineage. The applied episode also retains the same six unique Agent Run to Finding to Handoff chains consumed by that coordinator episode. Memory includes event class, flights, rotation, resources, policies, and a disruption signature. After replay reset, that applied lineage, action evidence, and the same six specialist chains return. A later decision uses that outcome only when its graph context matches, so a baggage memory cannot alter an unrelated weather decision.

For the third track, Operations Brain routes plain-language questions to ownership, incident, current-policy, or supersession traversals. Each answer returns evidence identifiers, its graph path, source excerpts, owner, responsible role, and current version. If the bounded company graph lacks support, it says the evidence is insufficient.

Publishing a replacement policy creates a `SUPERSEDES` relationship, advances graph state, and triggers replanning without changing application code.

GroundGraph uses the full official FalkorDB server locally through Podman and local Qwen through Ollama. Its improvements are projected under replay assumptions, never measured real-world savings. FalkorDB determines what the agents can see, which actions exist, who authorizes them, and which prior decisions are relevant next.
